# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

Skyglass is a native Android stargazing app (Kotlin, Jetpack Compose, OpenGL ES 3.0). Phase 1 is implemented: naked-eye stars (V ≤ 6.5, ~8,400) from the Yale Bright Star Catalogue are drawn on a black background in their true positions as the phone is pointed at the sky, using the rotation vector sensor, location, current time and magnetic declination. Also built: constellation lines and names, tap-to-identify (stars by name/designation, and the bodies below), and the Sun, Moon and the seven other planets (Mercury–Neptune), positioned for the current time and drawn distinctively, with the Moon showing its phase. Also built: a **Camera** switch (top right) that swaps the black sky for the live rear-camera image, with the stars, lines, bodies, labels and tap-to-identify still working over it (see "Camera view" below). Also built: a **Faintest stars** slider (opened by the "Display" button, top left) that dims the stars by a limiting magnitude (see "Faintest stars" below). Also built: a **horizon line, N/E/S/W (and NE/SE/SW/NW) letters and an altitude/azimuth reference grid**, with switches in the same "Display" card (see "Horizon and compass" below). Also built: a **Search** button (top left, beside "Display") that finds a star, constellation, planet, the Sun or the Moon by name and guides the user to it with an arrow at the screen edge and a marker (see "Search and navigation" below). Also built: tapping an object opens a details card (see "Object details" below): coordinates, altitude and azimuth, rise and set, and, for stars, spectral type, colour, constellation and distance, for bodies, phase, distance and apparent size. Also built: **deep-sky objects** (all 110 Messier objects plus about 65 other bright ones: the Magellanic Clouds, Omega Centauri, 47 Tucanae, the Double Cluster, the Carina Nebula, the Coathanger and so on), drawn as sized, per-type symbols, tappable, searchable ("M31", "NGC 224", "Andromeda Galaxy") and guided to, and a procedural **Milky Way band**, each with a switch in the "Display" card (see "Deep-sky objects and the Milky Way" below). Not yet built: zoom, night (red) mode, planetary moons (the Galilean moons sit within 0.2° of Jupiter, indistinguishable at this field of view until there is zoom), asteroids/comets, a photographic Milky Way, deep-sky objects beyond the bundled ~175, daylight sky (the horizon line is drawn, but nothing is shaded above or below it).

## Commands

All commands run from the repo root using the Gradle wrapper (`gradlew.bat` on Windows / `gradlew` in Git Bash).

- Build debug APK: `./gradlew assembleDebug`
- Full build (all variants, checks): `./gradlew build`
- Install on a connected device/emulator: `./gradlew installDebug`
- Run unit tests (JVM, `app/src/test`): `./gradlew test`
- Run a single unit test class: `./gradlew test --tests "com.skyglass.astro.CoordinatesTest"`
- Run a single unit test method: `./gradlew test --tests "com.skyglass.astro.CoordinatesTest.meeusExample13b_venusFromWashington"`
- Run instrumented tests (`app/src/androidTest`, needs a connected device/emulator): `./gradlew connectedAndroidTest`
- Lint: `./gradlew lint`
- Clean build outputs: `./gradlew clean`

Gradle is configured with the configuration cache enabled (`org.gradle.configuration-cache=true` in `gradle.properties`), and the daemon JVM toolchain is pinned to version 25 via `gradle/gradle-daemon-jvm.properties`.

## Architecture

- Single module: `app` (`applicationId`/`namespace` = `com.skyglass`). `minSdk` 28, `targetSdk`/`compileSdk` 37, Kotlin 2.2.10, AGP 9.3.3. CameraX (`camera-core`, `-camera2`, `-lifecycle`, `-view`, one `camerax` version) is used for the camera view. Versions live in `gradle/libs.versions.toml`; add dependencies there via the version catalog (`libs.*`), not as inline coordinates.
- **Rendering approach:** each star is converted once at load (proper motion + IAU 1976 precession) to a unit vector in the equatorial frame of date and uploaded to a static VBO. Each frame the GPU applies a single MVP built by `render/SkyViewMath`:
  `clip = P · S(displayRotation) · R(q)ᵀ · M(true→magnetic) · H(LST, lat) · v_eq`.
- **Sun, Moon and planets** use the same frame and MVP as the stars but move, so `SolarSystem.positions(julianDateUtc, lat, lon)` (pure Kotlin, `astro/`) is recomputed by `SkyViewModel` on every location fix and every 10 s while resumed, packed by `catalog/BodyVertices` into a separate small VBO and handed over through `SkyRenderInputs.bodyVertices` (the GL thread re-uploads when the array instance changes). Accuracy model:
  - Everything is the *mean* equator and equinox of date, like the stars: no nutation and no annual aberration (each < 20″; the stars omit them too, so everything stays in step). Time is UTC + 69.184 s (`AstroTime.julianEphemerisDay`) for the ephemerides.
  - Sun: Meeus ch. 25 (`SunEphemeris`, ~0.01°), geometric longitude (the Sun is at rest in the heliocentric frame, so this already includes light time). Moon: Meeus ch. 47, full 60+60 term series (`MoonEphemeris`, ~10″), geocentric then made **topocentric** by `Parallax` (vector method; the Moon's parallax is up to ~0.95°, so its direction depends on latitude and local sidereal time). Planets: JPL/Standish Keplerian elements for 1800–2050 (`PlanetEphemeris`; Standish quotes 15–40″ for Mercury–Mars but up to ~7′ for Jupiter and ~10′ for Saturn, i.e. 3–6 px at the current field of view, so **zoom will need a better theory** such as VSOP87), Earth taken as the Earth–Moon barycentre, three light-time iterations, J2000 ecliptic → J2000 equator → `Precession`. Planet parallax (< 0.003°) is ignored. Magnitudes are the Astronomical Almanac formulae (Saturn includes the ring tilt).
  - Rendering: `render/BodyShaders` draws point sprites with a per-kind look (`catalog/BodyAppearance`: planets tinted discs, Sun white-hot core and big glow, Moon a lit sphere). The Moon's lit side is computed on the CPU each frame by `SkyViewMath.spriteLight` (pure, unit-tested, including all display rotations) and passed as the `uMoonLight` uniform: sprite space is screen right/up with +z toward the viewer, z = −cos(elongation), lateral = sin(elongation) toward the Sun as projected on screen. The body pass uses premultiplied-over blending (`GL_ONE, GL_ONE_MINUS_SRC_ALPHA`): glows add, and the Moon is opaque only within its *true* angular radius (`uMoonOccluder`), because its drawn disc is ~4× too big and must not hide nearby stars or planets. Sprite sizes are exaggerated (the true Sun/Moon are ~7 dp). Known limitation: GL drops a point sprite once its centre leaves the screen, so the large Sun and Moon sprites vanish abruptly at the edge; fixing that needs quads instead of points. Tap reach is clamped to the GPU's maximum point size (`SkyRenderInputs.maxPointSizePx`). User-visible body and phase names live in `strings.xml` (`ui/BodyNames.kt` maps the enums).
  - `SkyBody` enum order is draw order (Moon last). Tap-to-identify prefers a body over a star when it is as close (`SkyHitTest.nearestBody`); labels and the selection ring come from the same `BodyPosition`s in `SkyUiState.bodies`.
- **Frame conventions** (pinned by unit tests; sign errors are the main risk when changing this code):
  - Equatorial: +X vernal equinox, +Z north celestial pole.
  - ENU: +X east, +Y north, +Z up. The rotation vector sensor's world frame is ENU with *magnetic* north; `Coordinates.magneticToTrueEnu` corrects it (declination positive east, as `GeomagneticField` reports).
  - Device (portrait) = OpenGL eye frame: +X right, +Y up, +Z out of the screen; the back of the phone looks down −Z.
  - Azimuth is measured from north through east (Meeus measures from south; tests note the conversion).
- Packages:
  - `math/`, `astro/`, `catalog/` (except `StarCatalog`), `sensors/OrientationFilter`, `render/SkyViewMath`, `render/CameraFov`, `astro/Galactic`, `catalog/DeepSky*` and `catalog/MilkyWay` (model, mesh, appearance, vertices; their GLSL strings in `render/DeepSkyShaders` and `render/MilkyWayShaders` are likewise plain strings), `render/OverlayBlend`, `render/SkyNavigation`, `render/HorizonGuides` (geometry and `CompassLabels`), `ui/CameraStateTracker` (also `CameraPermissionPolicy`): pure Kotlin with no Android calls, so they are covered by JVM unit tests. Keep new math there. (`BodyAppearance`/`BodyVertices` in `catalog/` and `BodyShaders` in `render/` are likewise Android-free strings/arrays.)
  - `sensors/`: `OrientationSensor` (TYPE_ROTATION_VECTOR → `AtomicReference<Quaternion>`), `LocationSource` (framework `LocationManager`, no Play Services; requests GPS directly with one listener per provider), `MagneticDeclination` (`GeomagneticField` wrapper).
  - `render/`: `SkyRenderer` (GL thread) smooths orientation once per frame with a quaternion slerp low-pass (`OrientationFilter`, time-constant based so it is frame-rate independent) and draws, in this order, the Milky Way band, the horizon guides (see "Horizon and compass"), constellation lines, the deep-sky objects (see "Deep-sky objects and the Milky Way"; their buffers arrive as `SkyRenderInputs.deepSkyVertices`/`milkyWayMesh`), then stars as `GL_POINTS` sprites with additive blending (in the enhanced view; the camera view blends "over" instead, see "Camera view"), then the Sun/Moon/planets. `SkyRenderInputs` holds `@Volatile` values handed from the main thread.
  - `ui/`: `SkyViewModel` (catalogue load, location → declination, body updates, tap selection, rise/set, view mode, UI state), `SkyScreen` (permission requests, `GLSurfaceView` in `AndroidView`, camera switch, status overlay), `ObjectInfoCards` (the tap details cards), `NavigationUi` (search button, search panel, guidance banner) and `CameraPreviewLayer` (CameraX preview + camera field of view). Sensors, location and the GL view are started and stopped via `LifecycleResumeEffect`.
- **Faintest stars** (the "Display" button, top left, opens the display card, `StarLimitSlider` and the horizon switches, in `SkyScreen`; `SkyUiState.limitingMagnitude`):
  - The setting is a limiting magnitude L, the faintest star the user wants to see, from 1.0 to 7.0 in steps of 0.1 (`StarVisibility.snapLimit`, applied in the view model, so the label, the Bortle class and what is drawn always agree). 7.0 (`MAX_LIMIT`, the default) is "all": the catalogue ends at 6.5 and the fade is centred on L, so every star is at full strength. The fade is a smoothstep over `FADE_WIDTH` = 1 magnitude centred on L: full strength at L - 0.5, half at L, nothing at L + 0.5, so dragging never pops stars in and out. Half strength is the midpoint, so "visible" means exactly `vmag <= L` (`isTappable`), which is what the label claims. It is a limit rather than a plain brightness scale because that is what the sky actually does under light pollution (faint stars vanish first, bright ones stay), and it maps onto the naked-eye limiting magnitude of a site.
  - Pure maths in `StarVisibility` (`visibility`, `isTappable`, `keepsSelection`, `snapLimit`; unit-tested). `StarShaders` repeats the expression (`1 - smoothstep(uLimitMag - 0.5, uLimitMag + 0.5, aVmag)`, with a test that the string agrees), using the star's magnitude, which `StarVertices` carries as an eighth float (`VMAG_OFFSET`). The factor multiplies the premultiplied colour, so in the camera view alpha (= max(r, g, b)) falls with it and the blending in `OverlayBlend` needs no change. Fully faded stars are moved outside the clip volume. The value reaches the GL thread as `SkyRenderInputs.limitingMagnitude` (`@Volatile`, set on every slider move).
  - Only stars are affected. The Sun, Moon and planets are brighter than any limit on the slider and are what the user orients by; constellation lines and names are navigation aids and stay (lines may therefore end at an invisible star).
  - Tap-to-identify ignores stars fainter than L (`SkyHitTest.nearestStar` takes the limit), and moving the slider deselects a selected star it excludes (`StarVisibility.keepsSelection`).
  - The slider is hidden until the "Display" button (48 dp, top left, mirroring the camera switch; open/closed state is `rememberSaveable`; it was labelled "Stars" before the horizon switches joined the card) is pressed, then shows as a card at the bottom under the status text. It was always visible at first; that covered about 100 dp of the sky (and the camera image), and Material's slider jumps to wherever its track is tapped, so a tap on a star near the bottom edge moved the limit instead. The trade-off: one extra tap to change the setting, and the card covers the bottom of the sky while it is open.
  - Persisted in SharedPreferences `display_settings` (`limiting_magnitude`, written when the drag ends), deliberately *not* excluded from backup, unlike `camera_permission_state`. Below the maximum the label also shows a rough Bortle class (`Bortle.classForLimitingMagnitude`, class limits from Bortle 2001 as tabulated on Wikipedia) so the user can match it to a site they know.
  - **Light pollution from GPS is not built.** Investigated: lightpollutionmap.info has an API (`QueryRaster`) but it refuses requests without a key obtained from its author and states no terms; the Falchi et al. 2016 World Atlas (the source of most such maps) is a 2.9 GB GeoTIFF, CC BY-NC 4.0 (so it can neither be bundled in a possibly commercial app nor is it small); the GFZ record we read says the full data is obtained through a request form (access to an FTP site) rather than a public download, which we could not re-verify on the live site, and the conclusion holds either way; David Lorenz's atlas is PNG maps with no stated licence and no point-query API; no keyless public lookup was found. The app also has no INTERNET permission. If one is added later it must be opt-in, off by default, with coordinates rounded to about 0.1°, and fall back silently to the slider. For converting a measured value, SQM (mag/arcsec²) to naked-eye limiting magnitude is NELM = 7.93 - 5·log10(10^(4.316 - SQM/5) + 1) (Schaefer 1990, as quoted by Unihedron); not implemented since nothing would call it yet.
- **Horizon and compass** (`render/HorizonGuides.kt`, pure and unit-tested in `HorizonGuidesTest`; `SkyUiState.showHorizon`/`showGrid`):
  - **Frame, and why not equatorial.** The geometry is a static VBO in **true ENU** (unit vectors from `Coordinates.horizontalToEnu`), drawn with `SkyViewMath.horizonModelViewProjection` = `P · S(displayRotation) · R(q)ᵀ · M(true→magnetic)`, i.e. the star MVP *without* `H(LST, lat)` (`viewMatrix` is now `horizonViewMatrix · H`, bit-identical to before). The alternative, converting the geometry to equatorial of date, would mean re-uploading it as the Earth turns (15° an hour) and needs time and latitude for something that depends on neither; in ENU the horizon is exact whatever the clock says and only the declination (true north) and the phone's orientation matter. A test pins that this MVP agrees with the star MVP once an ENU vector is carried to the equatorial frame, for all four display rotations. The renderer publishes the frame's matrix as `SkyRenderInputs.lastHorizonMvp` for the overlay (`lastMvp` stays the star one, which taps and navigation use).
  - **What is drawn.** The horizon is the great circle at geometric altitude 0° (sampled every 2°; no refraction, so it matches the "above/below the horizon" text on the cards). It is teal-green `(0.20, 0.55, 0.42)` (`LineShaders.HORIZON_*`), a different hue from the blue-grey constellation lines and clearly brighter, requested 2 px wide with `glLineWidth` (wide lines are optional in GLES, so many GPUs draw 1 px and the colour alone has to carry it; the width is reset to 1 afterwards). The **reference grid** is deliberately restrained: altitude circles at 30° and 60°, vertical lines at every 45° of azimuth (through N, NE, E, ... so they meet the compass letters) from the horizon up to 80°, and a small cross at the zenith (3° arms along the meridian and the prime vertical) instead of letting eight lines converge in a knot. The N-S vertical line is the observer's meridian. The grid is the horizon's hue at about a fifth of its strength, fainter than the constellation lines. Nothing is drawn below the horizon. Not drawn: the celestial equator, the ecliptic and an equatorial grid (they belong in the equatorial frame and would add clutter); a possible later addition.
  - **Drawing order and blending.** First, under the constellation lines and stars, with the same line program (`uCameraMode` makes alpha = max(r, g, b)) and the same blending as the lines (`OverlayBlend.stars`), so the camera view composites them "over" like everything else. At alpha 0.55 the horizon covers part of the camera image beneath it, as the brightest lines do. Not verified on hardware.
  - **Letters** (`CompassLabels`, drawn by `SkyOverlay` in Compose like the constellation names, with the `compass_*` strings the cards use): N, E, S, W bold and brighter, NE, SE, SW, NW smaller and dimmer, each with a dark shadow for the camera image. Each is anchored on the horizon at its true azimuth but raised `ANCHOR_ALTITUDE_DEG` = 1° of sky (about 13 dp at the default field of view) so the text rests on the line instead of being struck through; raising it in degrees rather than pixels keeps "above" meaning toward the zenith when the phone is rolled. `CompassLabels.place` projects through the horizon MVP and drops any point with clip w <= 0 (`SkyProjection.project` returns null, so a letter behind the viewer is never mirrored onto the screen) and any further than 24 dp outside the screen. True north comes from the same declination correction as the stars; tested with a sensor reading built independently of `magneticToTrueEnu`: with declination +10° a phone aimed at true north reports magnetic azimuth 350° and N lands at the centre; with the correction left out it lands 10° to the right.
  - **Switches.** The top row cannot take another control (Display, Search and Camera already fill about 360 dp), so the former "Stars" button is now **"Display"** and opens a card with the faintest-stars slider and, under it, one row of two 48 dp switches: **Horizon** (the line and the letters) and **Grid** (the card later gained a second row, **Deep sky** and **Milky Way**; see below). Both default to on and are stored in SharedPreferences `display_settings` (`show_horizon`, `show_grid`, written at once; in backups, like `limiting_magnitude`). The renderer reads `SkyRenderInputs.showHorizon`/`showGrid`; the overlay is given `showHorizon`. The card now covers about 200 dp of the bottom of the sky while open (slider, then the 2 × 2 switches), up from about 100 dp for the slider alone; the measured bottom panel keeps the guidance arrow clear of it. Not verified on a device: the card's layout at 360 dp wide, the 2 px line, the letters' size and shadow over a bright camera image.
- **Camera view** (the "Camera" switch in `SkyScreen`; `SkyUiState.viewMode`, `ViewMode.ENHANCED`/`CAMERA`):
  - Layers, bottom to top: `CameraPreviewLayer` (CameraX `PreviewView`, `PERFORMANCE` = a `SurfaceView`, `FILL_CENTER`), the `GLSurfaceView`, the Compose overlay (labels, ring) and cards. The GL view is always created with an RGBA8888 config, `PixelFormat.TRANSLUCENT` and `setZOrderMediaOverlay(true)`, so it sits above the preview's surface but below the window. `SkyRenderInputs.cameraMode` makes the renderer clear to transparent (alpha 0) instead of opaque black. The sky is drawn **over** the camera, not hidden, so tapping a visible star works as in the enhanced view. How much of the image each thing covers follows from its alpha (below): faint star edges and constellation lines hardly at all, bright star cores and the Sun's core and inner glow (alpha 1) completely, and the Moon's whole drawn disc (24 dp, about 4x the true size; its lit colour is 0.93, so alpha is about 0.93, also noted in the `BodyShaders` KDoc) almost completely, hiding the camera image and any star or planet behind it. In the enhanced view only the Moon's true-radius disc is opaque, so a planet near the Moon is hidden in the camera view where it would not be in the enhanced view; this was judged visually acceptable.
  - **Blending (`render/OverlayBlend`, pure and unit-tested):** the enhanced view is unchanged: everything adds to opaque black (`ONE, ONE` for colour, alpha untouched via `glBlendFuncSeparate`). In the camera view the surface is composited over the camera by the system, which expects *premultiplied* colour, and stars/lines/glows with rgb > 0 and alpha 0 are only valid by accident (anything that un-premultiplies the layer, e.g. colour-space conversion or Night Light in client composition, would drop them). So the shaders take a `uCameraMode` uniform (0/1) and output `alpha = max(r, g, b)` when it is 1 (`StarShaders`, `LineShaders`, `BodyShaders`), and the renderer blends everything "over" (`ONE, ONE_MINUS_SRC_ALPHA`), which keeps rgb <= alpha. Consequence: everything drawn *replaces* part of the camera image in proportion to its alpha instead of purely adding to it: a faint glow or line dims the pixels under it a little, a bright core or the Sun/Moon covers them. Not verified on hardware with Night Light or colour correction on.
  - **Field of view matching:** taps and labels use `renderInputs.lastMvp`, which is built with `renderInputs.fovYDeg` (default 60° in the enhanced view). In camera mode `CameraPreviewLayer` reads the bound camera's `LENS_INFO_AVAILABLE_FOCAL_LENGTHS`, `SENSOR_INFO_PHYSICAL_SIZE`, `SENSOR_INFO_PIXEL_ARRAY_SIZE` and `SENSOR_INFO_ACTIVE_ARRAY_SIZE` (via `Camera2CameraInfo`, opt-in `ExperimentalCamera2Interop`) and, once the stream is running and on every layout change, calls `CameraFov.forView` (pure, `render/CameraFov`, unit-tested) with the preview's `resolutionInfo` (stream size, rotation and crop rect) and the view size. That works out the focal length in view pixels, allowing for the HAL's aspect-ratio crop of the sensor (wider stream: full sensor width, top/bottom dropped; narrower: full height), any crop rect, and `FILL_CENTER`'s uniform scale-and-crop, and returns the vertical FOV for `SkyViewModel.onCameraFieldOfView` to put in `fovYDeg` (the Moon's true-radius occluder uses it too). The preview requests a 4:3 stream (the whole sensor on nearly all phones). If the characteristics cannot be read, `CameraFov.TYPICAL_PHONE` (about 67° along the sensor's long side) is used. Model limits: pinhole camera with the principal point at the view centre; lens distortion, an off-centre principal point, optical image stabilisation and digital zoom are ignored (a few tenths of a degree to ~1–2° at the edge of a wide lens). The focal length is the *first* of the camera's listed focal lengths, so on a logical multi-camera or optical-zoom phone that uses another lens at zoom 1.0 the FOV would be wrong by the ratio of the two; this is unverified on such hardware (`LENS_INTRINSIC_CALIBRATION` or a capture result's focal length would be exact but are missing or unreliable on many devices).
  - The camera looks along device −Z, exactly the GL eye frame's view direction, so no extra rotation is needed; the stream's sensor rotation is already undone by the preview. In camera mode `OrientationFilter.timeConstantSeconds` is `CAMERA_TIME_CONSTANT_SECONDS` (0.05 s) instead of 0.1 s. **This value is an untuned compromise:** filter lag makes the sky trail the image while panning, but the preview is itself tens of milliseconds behind the world, so too little smoothing makes the sky lead it and shows sensor jitter. Pan across a bright star on a device and adjust.
  - **Camera busy (stays in camera mode):** if another app holds the camera (`ERROR_CAMERA_IN_USE`, `ERROR_MAX_CAMERAS_IN_USE`), CameraX reports a `RECOVERABLE` error while in `PENDING_OPEN`/`OPENING` and keeps retrying. `CameraStateTracker` (pure, unit-tested; `CameraX` states mapped to its own enums in `CameraPreviewLayer`) turns that into `SkyUiState.cameraWaiting`, shown as a non-dismissing "Waiting for the camera..." line in the status overlay. Once waiting it stays up, even through error-free `OPENING`/`PENDING_OPEN` states published between retries, until the camera is `OPEN` (or a `CRITICAL` error leaves camera mode), on pause, or on leaving camera mode. The tracker ignores everything delivered synchronously inside `observeForever` (the previous session's stale `CLOSED` + error, possibly twice since `cameraState` is a mediator) and is armed by `tracker.attached()` right after it returns; it must not wait for a clean state instead, because `postValue` can coalesce a clean state and the new error into one delivery.
  - **Failure handling** (these drop back to the enhanced view and show a `CameraProblem` status message that clears after 8 s, only if it is still that message (`cameraProblemSeq`), or on the next touch of the switch or when the permission is found granted): permission denied (`PERMISSION_DENIED`); denied with "don't ask again" (`PERMISSION_BLOCKED`; `CameraPermissionPolicy`, pure and unit-tested, combines `shouldShowRequestPermissionRationale` read before the request (saved across recreation with `rememberSaveable`) and in the result, plus a flag for blocks already seen, persisted in SharedPreferences (`camera_permission_state`, excluded from backup and device transfer) because after a process restart the rationale is false both before and after an instantly refused request, so a dialog dismissed with Back is not mistaken for a block; the message then has an "Open settings" button to the app's details page, guarded against `ActivityNotFoundException`); permission no longer held on resume (e.g. an expired one-time grant; revoking in settings kills the process, so that case never gets here, while granting in settings does not and clears the message); `bindToLifecycle` throwing or no back camera, or the bound camera's `cameraInfo.cameraState` reporting a `CRITICAL` error: disabled by policy, fatal error, do-not-disturb mode or an unsupported stream configuration (`UNAVAILABLE`; `bindToLifecycle` does not throw for those, so the state is observed); and the `PreviewView` falling back to a `TextureView` on some legacy-HAL devices (`UNSUPPORTED`). A `TextureView` lives in the window, where the GL `SurfaceView` punches its hole, so the camera image would be wiped; the fallback is detected once the stream starts (a view-tree search for a `TextureView`; not exercised on such a device). Drawing the camera inside GL as an external texture would remove that limitation.
  - The `CAMERA` permission is requested only when the switch is first turned on. CameraX binds in a `LifecycleResumeEffect` and unbinds on pause or when leaving camera mode. `AndroidManifest.xml` declares `CAMERA` and `android.hardware.camera.any` as `required="false"`. The switch row is at least 48 dp tall.
- **Object details** (tapping a star, Sun, Moon or planet; `ui/ObjectInfoCards.kt` holds `StarInfoCard` and `BodyInfoCard`, which used to live in `SkyOverlay.kt`):
  - The card (top centre, under the two 48 dp toggles, at most 360 dp wide) always shows the name, designation or Moon phase, the magnitude, and a position line ("42.3° above the horizon · 135.2° SE" or "below"). A close button (48 dp, `SkyViewModel.clearSelection`; tapping empty sky still deselects too) and a full-width "More details" row (≥ 48 dp) sit on it. `detailsExpanded` (`rememberSaveable` in `SkyScreen`) is shared by both cards and deliberately kept across taps (so the choice sticks, and "Fewer details" is one tap away). Collapsed the card is roughly 150 dp tall including the toggle row; expanded, the detail rows scroll beyond 140 dp (`DetailRowsMaxHeight`), so it stays under about 300 dp. The card root swallows taps (`pointerInput`), so tapping its title or padding does not fall through to the sky underneath. Works in both views (it is a plain Compose overlay above the GL and camera layers).
  - **Stars** (`StarDescription`, built by `StarNamer.describe`): constellation name, MK spectral type, colour name (`SpectralType.colorName`: from the class letter, else B−V) with B−V, distance, RA/Dec of date, rise/set, HR number. `Star` now carries `spectralType` (BSC columns 128-147) and `parallaxArcsec` (162-166, written "+.375"), parsed by `BscParser`.
    - **Distance** (`StarDistance.fromParallax`, `catalog/StarDetails.kt`) is d = 3.2616 ly / parallax. The BSC (1991) predates Hipparcos, so its parallaxes are ground-based with errors of roughly 0.005–0.01″, and 388 entries (column 161 `D`, `Star.parallaxDynamical`) are dynamical parallaxes worked out from binary orbits, not measured. So: ≥ 0.05″ is shown as "about N light years" (two significant figures); 0.02–0.05″ as "roughly N light years (uncertain)"; below 0.02″ or absent as "not known reliably from the catalogue" (dynamical ones are always shown as rough; Betelgeuse's 0.005″ and Polaris's 0.007″ are limits, not measurements). About 3,300 of the 9,100 records have a parallax. No claim is made beyond that: Sirius comes out at 8.7 ly (true 8.6), Vega 27 ly (true 25).
    - **Constellation** is the catalogue's abbreviation (only stars with a Bayer or Flamsteed designation have one, ~3,100 naked-eye stars), else the constellation whose stick figure contains the star (`StarNamer`, skipping stars two figures share). That still leaves about 63 % of the naked-eye stars with no constellation (the row is then omitted): there is no boundary table. This is a known limitation: the IAU boundaries (Delporte, B1875; machine-readable as the Roman 1987 table, CDS VI/42) would fix it but are not bundled. Serpens' two figures are reported as "Serpens".
  - **Bodies** (`BodyPosition`): illuminated fraction (Moon, Mercury, Venus), elongation, distance (km for the Moon, AU otherwise), apparent diameter (`astro/BodySize`: IAU nominal Sun radius, mean Moon radius, planets' equatorial radii; arcminutes for the Sun and Moon, arcseconds for planets; the Moon uses its geocentric distance, so its size is up to ~1.7 % off from the observer's; rings excluded), RA/Dec of date, rise/set.
  - **Position** is computed in the UI from the object's equatorial-of-date unit vector by `astro/SkyPlacement.of` (RA/Dec of date, geometric altitude, azimuth from north through east), using `SkyUiState.julianDate`, the time of the last body update (so it updates every 10 s, during which the sky turns 0.04°). No atmospheric refraction in the displayed altitude; no nutation or aberration, as everywhere. `CompassPoint` (8 points) and `Sexagesimal` (rounds to whole seconds with carries, 24h wraps to 0h) are pure and tested. RA/Dec are labelled "of date", not J2000.
  - **Rise and set** (`astro/RiseSet`, pure): a 10-minute scan of altitude over the next 26 h (`WINDOW_HOURS`; the Moon can go 25 h between risings) with bisection to ~0.15 s (and, where the altitude turns within 1° of the horizon without crossing it, a search for the turning point, so a rise and set less than a step apart are not lost), returning the first rising and first setting, or "stays above/below the horizon" when neither occurs. The body ephemeris is re-evaluated at each step (`SolarSystem.position`, new, same values as `positions`), so the Moon's own motion is included (using its current position for the whole day would be off by tens of minutes). Horizon altitude: −34′ for stars and planets (standard refraction), −50′ for the Sun, −34′ minus the Moon's semi-diameter (≈ −0.82°) for the Moon, whose position is already topocentric. Tested against Meeus 15.a (Venus at Boston, within 1 min), US Naval Observatory sun and moon rise and set for London (21 Jun and 8 Oct 2026) and Madrid (22 Oct 2026), fetched from its API on 2026-10-08 and quoted to the minute in `RiseSetTest` (2 min tolerance), Tromsø's midnight Sun and polar night, and the Moon. It runs on `Dispatchers.Default` in `SkyViewModel.refreshRiseSet` (a few hundred ephemeris evaluations, about 10 ms), on each selection and each body update, with a `checkActive` hook (`ensureActive`) called before every altitude evaluation so a superseded calculation stops at once; a result for something no longer selected is dropped, and `SkyUiState.riseSet` is null until it arrives (the rows are simply absent). Times are shown in the device zone, in 12 or 24 hour form as the system setting says (`DateFormat.is24HourFormat`), with the weekday when not today. They do not allow for terrain or the observer's height, and use geometric altitude with the standard 34′ refraction, so can differ from an almanac by a minute or two.
  - Text is in `strings.xml` (`detail_*`, `compass_*`, `star_color_*`; `body_illuminated`, `body_elongation` and the `body_distance_*` strings are now values without the words that used to follow, since they sit in labelled rows). Tested in `StarDetailsTest`, `StarNamerTest`, `SkyPlacementTest`, `BodySizeTest`, `RiseSetTest` and `BscParserTest`. **Not verified on a device**: the card's layout (heights, scrolling, the 360 dp width) was written without running the app.
- **Search and navigation** (the "Search" button, top left beside "Display"; `SkyUiState.navigation`, `SkyViewModel.search`/`navigateTo`/`stopNavigation`):
  - **What it finds** (`catalog/SkySearch.kt`, `SkySearchIndex`, pure, unit-tested in `SkySearchTest`): the Sun, Moon and planets by name; constellation figures by name (one entry per *label*, so Serpens gives "Serpens Caput" and "Serpens Cauda", and a figure spread over opposite sides of the sky, which has no label, cannot be found); stars by traditional name, designation (typed "α Canis Majoris", "alpha canis majoris", "alpha cma" or "alpha CMa"; "61 Cygni" or "61 cyg"; the Bayer superscript may be left out, so "alpha centauri" finds α¹ and α²) or HR number ("hr 2491", "2491"). Only the ~8,400 naked-eye stars the sky draws are indexed. `normalize` lower-cases, strips accents (NFKD), spells Greek letters out (α¹ becomes "alpha1") and turns every other run of non-alphanumerics into one space. Each entry has several normalised keys and its rank is its best key's tier (whole name, start of name, start of a word, every query word starting some word in any order, anywhere in a word for queries of 3+ letters), then bodies before constellations before stars, then brighter stars, then title. At most `MAX_RESULTS` (20). An empty query suggests the bodies and then the brightest stars that have a traditional name. It is a linear scan over a few tens of thousands of keys per keystroke on the main thread (expected to be a few ms; not measured on a device). Built once on the IO thread with the catalogue (`LoadedSky.searchIndex`); body names are localised there with `Application.getString`, so a language change while the process lives is not picked up. Until the catalogue has loaded the index is null: search returns nothing and the panel says "Loading stars…". Not searchable: a star's Flamsteed number written with the full genitive when it also has a Bayer letter ("9 Canis Majoris"), Gould numbers, variable-star names, other catalogues. Deep-sky objects are indexed too (see below). There are no planetary moons in the app.
  - **Guidance** (`render/SkyNavigation.guide`, pure, unit-tested in `SkyNavigationTest`; drawn by `SkyOverlay`): from the latest frame's MVP (`renderInputs.lastMvp`, so it uses the camera's field of view in the camera view and the display rotation automatically) and the target's equatorial-of-date direction it returns the angle between the view centre and the target (clip w of a unit vector is its cosine, because the view matrix is a rotation and the projection's w row is `-z`), where the target is drawn if it is on screen, and, unless it lies inside the *usable* rectangle, an `EdgeArrow`: where the ray from the screen centre toward the target meets that rectangle, and an angle in screen space, clockwise from pointing right (screen y points down; this is the sense of Compose `rotate`, so the overlay rotates a right-pointing arrow by it). The direction comes from clip-space x, y (scaled to pixels, y negated), not from the projected point, so it stays right for a target **behind** the viewer (clip w < 0), where the perspective divide would mirror it through the centre: a target behind and to the right gets an arrow pointing right (turn that way); this is tested against the target's mirror image through the view plane for all four display rotations. Dead behind has no better answer than "right". The usable rectangle is the screen less `NavInsets`, clamped so the screen centre is always inside it; `SkyScreen` builds the insets from the system bars, the 48 dp toggle row, the measured bottom of the details card (`onGloballyPositioned`, counted only while a card is showing), the measured top of the bottom panel and a 28 dp margin for the arrow, so the arrow does not hide under a card, toggle or the slider. A target that is on screen but under a card gets both the marker and an arrow. The arrow is amber (`NavigationColor`) with a dark outline (for the camera image) and is labelled with the degrees still to turn (`angularDistanceDeg`, rounded). A target in view gets a ring with four ticks outside the plain selection ring: 28 dp for a star, the disc plus 18 dp for a body, 64 dp for a constellation (whose position is its label anchor, the mean direction of its figure's stars, so the marker means "the middle of it").
  - **Flow and UI:** the "Search" button (`SearchToggle`, `ui/NavigationUi.kt`) opens `SearchPanel` at the top centre, where the details card normally is (the card is hidden while the panel is open): a text field (the keyboard's search key chooses the first result), a 48 dp close button and a scrolling result list (rows ≥ 48 dp, at most 288 dp tall) showing title, designation or constellation and kind. Back closes it. The query is `rememberSaveable`. Choosing a result calls `SkyViewModel.navigateTo`, which **selects the object** (a star or body: the existing details card opens and rise/set is calculated; a constellation has no card, so the selection is cleared) and sets `navigation` (a `NavigationTarget`: the result plus a fixed direction for stars and constellations; a body's direction is looked up in `SkyUiState.bodies` each frame so it follows the body). A banner at the top of the bottom panel says "Finding X", adds "Below the horizon, toward SE" when the target's geometric altitude (`SkyPlacement` at `SkyUiState.julianDate`) is negative, adds "Hidden by the faintest-stars setting" for a star the slider excludes (`StarVisibility.isTappable`; it is still guided to and ringed), and has a 48 dp "Stop" button (`stopNavigation`; the object stays selected). Guidance ends only with Stop: tapping the sky, closing the card, the camera switch and the slider do not end it, and searching again replaces the target. It works in both views, being a Compose overlay and a CPU projection with `lastMvp`.
  - **Not built / limitations:** no "on target" confirmation beyond the marker appearing; no haptics or sound; no recent or favourite searches; a constellation's guided position is its figure's mean direction; the below-horizon hint compares geometric altitude with zero (no refraction). **Not verified on a device**: the search panel with the keyboard open (the panel is top-aligned, and `safeDrawingPadding` lifts only the bottom panel), the measured insets (the first frame after a card appears uses the previous measurement), whether the three toggles (Display, Search, Camera) fit side by side on narrow screens (estimated to fit 360 dp), and how the arrow reads over a bright camera image.
- **Deep-sky objects and the Milky Way** (`SkyUiState.showDeepSky`/`showMilkyWay`, the second row of switches in the "Display" card; `SkyRenderInputs.deepSkyVertices`/`milkyWayMesh`):
  - **Data and licence** (`app/src/main/assets/deep_sky.txt`, parsed by `DeepSkyParser`; the file header documents each column): 176 objects, one per line: designations (`M31;NGC 224`, `C 14` for the Caldwell number), common name, aliases, type (`DeepSkyType`: galaxy, globular cluster, open cluster, emission/reflection/planetary nebula, supernova remnant, dark nebula, star cloud, asterism, double star), J2000 RA/Dec as `hh:mm:ss`/`±dd:mm:ss`, integrated visual magnitude (none for the Coalsack), size (long and short axis in arcminutes), position angle of the long axis (north through east, optional) and the full IAU constellation name. It holds all 110 Messier objects (M40 is a double star and M73 an asterism, as catalogued; M102 is NGC 5866, M91 NGC 4548 and M48 NGC 2548 by the modern identifications) and 66 others: both Magellanic Clouds, 8 globular clusters (Omega Centauri, 47 Tucanae, NGC 6397, 6752, 362, 3201, 2808, 1851), 25 open clusters and asterisms (Hyades, both halves of the Double Cluster, Alpha Persei and Coma clusters, the Coathanger, the Jewel Box, the Southern Pleiades, ...), 13 nebulae (Carina, North America, both Veil arcs, Rosette, Tarantula, Helix, Cat's Eye, Eskimo, Saturn, Ghost of Jupiter, Blinking Planetary, the Coalsack), and 18 other galaxies (Sculptor, Centaurus A, NGC 55, 300, 4945, ...).
  - **Provenance, honestly:** there is no INTERNET permission, so the data is bundled. The Messier rows were transcribed from published Messier tables and checked against the table on Wikipedia's "List of Messier objects"; the other rows are hand-tabulated, with their Caldwell numbers, types and constellations checked against Wikipedia's Caldwell list, and about a dozen positions spot-checked against its NGC lists. Positions, magnitudes and sizes are astronomical facts, which carry no copyright, and nothing was copied from a database file or its layout. **OpenNGC (CC BY-SA 4.0, share-alike) was deliberately not used**; if the catalogue is ever extended from it, its attribution and share-alike terms need a decision first. Accuracy: Messier positions to better than an arcminute, the others to a few arcminutes (a pixel is about 1.5′ at the default field of view); magnitudes are integrated visual ones that differ by several tenths between sources and mean little for the largest objects; sizes are approximate and position angles good to perhaps 20°; a few rows (open clusters quoted to 0.1 minute of RA) are coarser. About 45 of the 66 non-Messier rows had their position checked against Wikipedia infobox values, which found NGC 6025 mis-entered by 26 minutes of RA (now 16h 03.7m, pinned by a test) and moved the Mel 20, Mel 111, IC 4756 and NGC 6633 centres by up to 0.6°. The remaining ~20 (e.g. NGC 7000, the Veil arcs, NGC 55, NGC 3532, NGC 457's size) were not independently checked. A script cross-check of each row's stated constellation against the nearest Bright Star Catalogue stars flagged only genuine border cases, but note that no automatic test can catch an error that stays inside the right constellation (`DeepSkyTest` only rejects objects more than 20° from every star of their stick figure). M8 and M24 deliberately carry the magnitudes of the usual Messier tables (6.0 and 4.6), not the 4.6 and 2.5 that Wikipedia's table prints, because the magnitude sets the drawn strength and 2.5 would make the huge M24 star cloud as strong as a bright cluster. This is a viewing aid, not a research catalogue.
  - **Positions** are precessed from J2000 to the mean equator of date once at load (`DeepSkyVertices.directions`, the same matrix as the stars; no proper motion, which is negligible), so they sit in the same frame and MVP as everything else and stay as fresh as the stars do (computed when the process starts).
  - **Drawing** (`render/DeepSkyShaders`, `catalog/DeepSkyAppearance`, `DeepSkyVertices`): not point sprites, because the GPU's maximum point size (often 64–256 px) is far too small for the Andromeda Galaxy (3° across, ~120 px at 60°) or the Large Magellanic Cloud (10°, ~400 px) and a sprite vanishes when its centre leaves the screen. Each object is two triangles (six vertices of 12 floats, `GL_TRIANGLES`) that the vertex shader builds in the tangent plane at the object: long axis along the position angle (north through east in the equatorial frame of date, east = z × direction; the CPU twin `DeepSkyGeometry.cornerPoint` pins the orientation in `DeepSkyTest`), semi-axes in tangent-plane units, enlarged until the long semi-axis is at least `MIN_RADIUS_DP` (7 dp) so a 20″ planetary nebula still shows (the shape is kept; `DeepSkyAppearance.drawnSemiAxes` repeats the sum for taps and labels). An object whose position angle is unknown is drawn round (`DeepSkyObject.drawnMinorArcmin`) rather than as an ellipse with a made-up direction. The fragment shader draws a symbol per kind, with the ellipse's edge at distance 1: a glow with a nucleus (galaxy), a dense ball (globular), a dotted ring (open cluster, asterism, double star), a soft disc (emission/reflection nebula, star cloud), a ring round a bright centre (planetary), a thin ring (supernova remnant) and a faint dashed outline (dark nebula), each in its own hue (lilac, amber, yellow, pink, blue, green, teal, grey). Strength comes from *surface brightness* (the magnitude spread over the ellipse, `surfaceBrightness`), not magnitude, so a huge object of magnitude 1 is fainter per pixel than a small bright one, times a gain of 0.7 so the symbols never rival a bright star.
  - **Order and blending:** Milky Way, horizon guides, constellation lines, deep-sky objects, stars, then the bodies, so stars and planets are always over a symbol. Deep-sky objects and the band use the star blending (`OverlayBlend.stars`) and the same `uCameraMode` rule (alpha = max(r, g, b)), so in the camera view they veil the image in proportion to their own strength. Each frame the renderer disables vertex arrays 0–6 first, since the passes use different attribute layouts and buffer sizes.
  - **The faintest-stars slider does not affect them.** The slider is a *star* limiting magnitude; integrated magnitudes of extended objects are not comparable with it (a magnitude 9 galaxy is much harder to see than a magnitude 9 star, and a magnitude 4 cluster 1° across is not hidden by a limit of 4), and at the default "all" (7.0) most galaxies would vanish. They have their own switch instead. Taps, labels and search ignore the slider, and `NavigationBanner` shows "Deep-sky objects are switched off in Display" for a target while its switch is off. Switching them off deselects a selected one.
  - **Labels** (`DeepSkyLabels`, drawn by `SkyOverlay` in lilac): a named object that is brighter than magnitude 5 or larger than 2° (Andromeda Galaxy, Orion Nebula, Pleiades, Magellanic Clouds, Omega Centauri, Carina Nebula, Double Cluster, ...) is labelled with its name, and any other Messier object brighter than magnitude 6 with its number ("M13"); 47 in all, so the Sagittarius/Scorpius region is busy. The label sits below the symbol, or in the middle of a symbol over 60 dp in radius. The rest can still be tapped and searched for.
  - **Tapping** (`SkyHitTest.nearestDeepSky` and `SkyHitTest.choose`, both unit-tested in `DeepSkyHitTestTest`): the hit area is the object's drawn *ellipse* on the screen (the semi-axis ends are projected through the frame's MVP, so the long axis, short axis, position angle and the minimum size are all respected; an object with no position angle is a circle) or a fingertip (24 dp) round its centre, whichever is larger, so taps beside a thin galaxy miss it. For the contest with stars and bodies, an object's distance is the distance to its centre if it is small, and, inside a big one, the tap's radius in the ellipse (0 at the centre, 1 at the rim) times a fingertip. So a tap in the middle of the Large Magellanic Cloud, the Pleiades or the Carina Nebula selects the object even with a star 40 px away, a tap right on a star inside it selects the star, and near the rim a star within a fingertip wins as anywhere else. `choose` then gives a body a tie with a star, a star only if strictly nearer than the body, and a deep-sky object only if strictly nearer than any star or body (stars and bodies are drawn over the symbols). The selection ring follows the object's extent up to 140 dp.
  - **Details card** (`DeepSkyInfoCard`, `ui/ObjectInfoCards.kt`, sharing `ObjectCard` and `detailsExpanded`): always the name, other designations, type and magnitude, and the position line; expanded, type, constellation, apparent size ("3.2° × 1.0°", "8.7′ × 6.5′", "18″"; only one value for a round object), RA/Dec of date and rise/set (`RiseSet.forStar`, the object being a fixed point, with the stars' refraction allowance). No distance is shown: the catalogue has none. Strings are `dso_*`, `detail_size_*` and `guide_deep_sky`/`guide_milky_way`.
  - **Search and guidance** (`SearchTarget.DeepSkyTarget`, `SearchKind.DEEP_SKY`, ranked after constellations and stars on equal matches, so typing "alpha pers" or "tau canis" finds the star before the cluster named after it, while the cluster's full name finds the cluster; `SearchResult.rankMagnitude` breaks ties by brightness): "M31", "m31", "m 31", "Messier 31", "NGC 224", "NGC224", "C 14", "Caldwell 14", "Mel 25", "Cr 399", the common name ("Andromeda Galaxy", "Orion Nebula") and aliases ("Praesepe", "Seven Sisters", "LMC") all find an object, an exact match before the longer numbers that merely start with it ("m1" before "m10"). The empty-query suggestions do not include them. Guidance works as for a star (a fixed direction; `SkyNavigation.guide` needed no change), with a marker that grows to the object's extent (up to 160 dp), and choosing a result selects the object and opens its card.
  - **Milky Way** (`astro/Galactic`, `catalog/MilkyWay`, `render/MilkyWayShaders`): the IAU galactic frame (north galactic pole RA 192.85948°, Dec +27.12825°, l of the north celestial pole 122.93192°) is built in `Galactic` from those three numbers; tests give the galactic centre at RA 266.405°, Dec −28.936°, the pole and the NCP exactly, and the galactic coordinates SIMBAD lists for Vega, Sirius, Deneb, M31 and Sgr A*. The band is **procedural**: `MilkyWayModel.brightness(l, b)` (0 to 1) is a sum of Gaussians in galactic longitude and latitude (a thin disc brighter and thicker toward the centre and about 40% as bright at the anticentre, the bulge, and star clouds in Sagittarius, Scutum, Cygnus, Perseus-Cassiopeia, Carina, Crux-Centaurus and Norma) times dark lanes (the Great Rift along the plane from l = −35° to +90°, rising to the Ophiuchus dark clouds by the centre, and the Coalsack), with a warmth that turns the inner band yellow-white. It is qualitative, not a survey: features are right to a few degrees and the shapes are idealised; real detail (the Pipe Nebula, fine dust lanes, the Cygnus rift's branches, the zodiacal light) is missing. No texture is bundled because no suitably licensed all-sky image was at hand and one would be large. `MilkyWayMesh` evaluates it on a grid of 1.5° in longitude and 29 latitude rows from −40° to +40° (closer together near the plane), turns each vertex to a unit vector of date (precession applied) and a premultiplied colour (`PEAK_INTENSITY` 0.24 at the brightest), and draws it as an indexed triangle mesh (7,000 vertices, 16-bit indices) that the GPU interpolates; the edge rows are essentially black so the band has no visible edge. The fragment shader adds interleaved-gradient noise of ±½ of an 8-bit step, because a gradient at an intensity of 0.05 would otherwise band. **It must not wash out the camera image:** over the camera it is drawn at `MilkyWayAppearance.CAMERA_GAIN` (0.5) of its strength, i.e. an alpha of at most 0.12, so about 88% of the image survives under the brightest part (tested). It is drawn whatever the Sun's altitude (there is no daylight sky) and whether or not the horizon hides it.
  - **Not verified on a device** (none was available): how any of it looks, i.e. the symbols' hue and strength over the black sky and the camera image, label clutter, the glow's size against the true extent, the Milky Way's overall brightness and banding, GLSL compile on real drivers (the shaders were reviewed, not run), draw cost (about 1,000 vertices and 13,000 mesh triangles, expected to be negligible), and whether the 2 × 2 switch card fits at 360 dp. Also not built: per-object distance, finer position angles, deep-sky objects below the horizon being hidden, thinning labels by field of view (there is no zoom), and a user-adjustable Milky Way brightness.
